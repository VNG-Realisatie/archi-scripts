# View testability and readability refactor

Rename on approval to `plan/view-testability-readability-refactor.md` (repo hard rule 8 "Plans live in `plan/`": descriptive name, never a generated one).

## Context

Goal: more of `Scripts/View/lib` testable in Node, smaller files that are cheaper to read (context and tokens), and a harness that is as small as possible. Today the purity of a function is per-function convention (ARCHITECTURE § Runtimes), the writer and Graphviz run only in Archi, and `tools/view_harness.js` copies the orchestration of `_generateSingle` (`maskPreset`, `resolve`, `layoutGraph`, `layout`) and models the writer (`simulateWrite`), so it can drift from the real run.

Approach: functional core, imperative shell. Archi reader → snapshot of plain records → pure plan (object set, nesting, layout graph, layout, write plan) → thin Archi apply. Files are cut along subjects; purity is per file and checked by the typecheck.

## Pros and cons (this repo)

| Pros | Cons |
|---|---|
| Writer, bendpoints, step expansion, dialog counts and Graphviz become testable in Node; "view looks wrong" cases that live in the writer can be reproduced in the harness. | The writer refactor carries the most regression risk, and only Archi shows rendering; each milestone needs an Archi run. |
| One `plan()` used by Archi and the harness: the harness cannot drift from the real run, and shrinks to a model reader plus CLI. | The snapshot is a new contract (types in `types/view.d.ts`) with two implementations: the jArchi reader and the `.archimate` reader. That drift already exists, but becomes explicit. |
| A pure jsconfig makes `$` in a pure file a type error instead of a harness surprise. | `jarchi.d.ts` is split in two; the skill and `types/README.md` follow. |
| Smaller files cut along subjects: an agent reads one tab or one phase, not 3500 lines. | Moved helpers lose `_` at every call site in the same commit (hard rule 3 "No backwards-compat fallback for renames"), so diffs are large. |
| Explicit exports replace `// ──` comments as boundaries. | ARCHITECTURE tables, Run flow and `repo-guide` change with each milestone; blame needs `git blame -C -C`. |
| | No runtime gain (modules are memoised). |

## Baseline (before any code change)

- **Layout digests:** `node tools/compare-layouts.js` on every test view × the tracked `presets/Test/*.json` (every algorithm per preset).
- **Written-view diff:** new `Scripts/View/tools/compare-views.js <old.archimate> <new.archimate> <folder>`. It prints per view a canonical text: each visual as concept id + parent concept chain + occurrence index, bounds, bendpoints, managed-occurrence records, connections by relation id. Visual ids are left out because they differ per run. New `Scripts/View/test/run_baseline.ajs` runs the fixed action × view × preset matrix through `generate_view`, so an Archi baseline is one script run; it saves the result as `Scripts/View/test/model/view-baseline.archimate`, committed, so every later session compares against the baseline of the commit it starts from.
- **Write-plan snapshots** (from milestone 3): the harness dumps the write plan as JSON per test view; diff before and after.

**Test model:** a separate model tracked in the repo, `Scripts/View/test/model/view-test.archimate`, so the Node tests and CI need no model from outside the repo. Nobody builds it by hand: `Scripts/View/test/build_test_model.ajs` (written by the agent, using the jArchi model API looked up in `jarchi.d.ts`) creates a new model with the elements, relations and the three views below. View 2 is made by the script too: it runs NEW_VIEW on view 1's content, then applies the hand edits through the API. You run it once in Archi and save the model at that path. To change the test data, edit the script, rerun it and commit both.

**Minimal test views (3):**
1. **Nesting:** composition and aggregation chains; one element with two parents (several occurrences); a nesting cycle; a reversed relation type; a self-loop; a relation between elements in different containers; a note with a connection and a group (diagram objects, diagram blocks). Covers the pipeline, nesting, the layout graph, cross-container edges and self-loops.
2. **Edited:** view 1 generated once, then edited by hand: one visual moved into another container, one user connection, one element added. Covers managed occurrences, pairing, and keep/move/create/remove in EXPAND_VIEW and LAYOUT_ONLY.
3. **Network:** 15–25 elements, no nesting, mixed relation types with labels, two disconnected parts. Covers routing, label positions, Pack/Grid, Circo's second process and Twopi rings; ONE_EACH on two of its elements.

Archi matrix: NEW_VIEW on 1 and 3, EXPAND_VIEW and LAYOUT_ONLY on 2, ONE_EACH on 3. Presets: `baseline.json` (Layered; nesting, a reversed type, one step, a style rule; made for the test model, as `test-preset.json` has none of these) and `AlgoTwopi.json` (Graphviz) = 10 runs.
